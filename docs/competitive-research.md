- Coupon / budget / cheapest-meal optimizers: many names plus substantial implementations, not all thin wrappers.
- Party availability, group meals and group fairness: at least three strong existing approaches.
- Nutrition/calories, persona cards/pets, annual report and campaigns: repeatedly present.
- Developer CLI/probe: already present too; differentiation must be a narrow verifiable guarantee.
- Points expiry and redemption ledger: already a mature inspected example.

The inspected sample is unusually implementation-rich. It would be inaccurate to label every competitor a “thin AI wrapper.” Some entries rely Agent normalization and assumptions, but several contain deterministic engines and defensive transport.

## Evidence-backed pain points versus hypotheses

**Observed in code/docs across independent submissions** (third-party implementation evidence; revalidate against official/live service before adopting):
1. Response is often Markdown with `## Original Response`, not directly JSON.
2. Several tools return Chinese empty text; empty versus failure must not collapse.
3. Tools actually reported as 35 vs 33 in README; date/session tool-name discrepancies.
4. Same product code/name varies across stores and dayparts; conditional membership price differs from actual quoted basket.
5. Server may omit coupon IDs and machine-readable eligibility details; generic optimizer cannot safely invent them.
6. Skill authors repeatedly build their own transports and parsers, with differing behavior. Contract tests and fixtures are a reusable developer need.

**Product hypotheses requiring validation**:
- An MCP contract regression/record-replay kit would save integration maintenance time. Evidence establishes technical failure modes, but no interviews/time-saving measurements conducted.
- A pre-order receipt guard would reduce wrong-store/unknown-configuration mistakes. No user incidence rate measured.
- A change-aware menu watch would help people check favorite product availability. No recurring demand interviews conducted.

## Recommended differentiated direction

A narrowly scoped **read-only MCP contract guardian** for independent developers: pull current tool schemas without business writes; compare additive/breaking changes; inspect response envelopes; produce a sanitized, portable evidence bundle and replay known response-shape fixtures. It could include a realistic store→menu→detail→quote contract as an opt-in verified journey, but should not auto-probe sensitive tools. Distinction from existing explorer: no arbitrary auto calls, no guessed parameters, no mock fallback masquerading live, structural change impact, executable assertions, redaction defaults and CI-compatible offline replay. Useful after the contest; measurable results are detected fixture regressions, zero write dispatches and reproducible reports.

Alternative consumer angle: **basket handoff/receipt guard** that checks a user-supplied intended cart against official quote, validates store/channel/date/product identity, displays discrepancies and never orders. More immediate consumer value but less reliable without authenticated schemas.

Do not clone an optimizer or generic party planner. Do not use unsupported nutrition ingredient/allergen data or fabricate “savings.”
